# Offline auditní přepočet · metodika pro 0.6.17

Základ kódu: ce34eae8c3a97f37facf0668353e459754889c89.
Tento příspěvek přidává samostatný offline nástroj a syntetický regresní
kontrakt. Produkční runtime, HA karta a verze se nemění.

## Proč oddělit předpoklady

Historický last_reported není sám o sobě důkazem, kdy mohl konkrétní worker
report převzít. Nové časování smyčky proto nelze zpětně ověřovat tím, že
všechny historické reporty bez označení zpřístupníme v jejich timestampu.
Hladší retrospektivní graf by tak mohl pouze skrývat předpoklad dostupnosti.

Nástroj scripts/replay_archived_night.py uvnitř priority_shadow vytváří
tři samostatné archivy:

| Varianta | Dostupnost vstupů | Předpoklad vlastníka |
|---|---|---|
| strict_capture | Nejnovější původně zachycený snímek | Nedoložený heartbeat se nedoplňuje. |
| captured_owner_assumed | Stejná zachycená dostupnost | Čerstvost dvou owner entit se předpokládá podle run-mode reportu. |
| report_time_owner_assumed | Předpokládaná okamžitá dostupnost při last_reported | Stejný předpoklad owner heartbeat. |

Varianty nejsou dolní/horní matematické meze fyzického výsledku.
Liší se dostupností vstupů a výsledek nelze vydávat za skutečně nabitou
energii nebo nový živý běh. Zdrojové hodnoty a původní report timestampy
rychlých senzorů se nepřepisují. Model se smí použít pouze po model_available_at.
Produkční next_wait se volá s výslovně uvedeným předpokladem nulové délky
práce. Zaznamenané selhání sběru a interval do zachyceného zotavení zůstávají.
Přísná kontrola může správně odmítnout převzetí, pokud není heartbeat doložený.

## Použití a ochrana zdrojů

CLI argumenty: read-only SQLite snapshot, gzip JSON historie, den YYYY-MM-DD,
nový neexistující výstupní adresář. Všechny skutečné vstupy i výstupy se
zpracovávají a uchovávají pouze na autorizovaném RPi.
Nástroj nevolá HA, nemá akční adaptér a nepublikuje data. Každá varianta
obsahuje vlastní provenienci, SQLite a JSON archiv.
Existující výstup se odmítne; původní evidence se neaktualizuje.
Ideální model se explicitně označí unavailable, aby karta nemohla převzít
výsledek jiné živé relace při chybějící hodnotě rekonstrukce.

## Syntetické ověření

test_archived_replay.py prochází cestu fixture → RAM → SQLite → tři archivy
a nezávislou integraci energie. Ověřuje neměnnost zdrojové DB,
odmítnutí existujícího výstupu a budoucího modelu, odlišné provenience a nulové
fyzické akce. Původní neúspěšné syntetické fixture i opravené výsledky jsou
v replay-evidence-0617/replay-test-v1.log až v4.log.
Před doplněním negativního kontraktu prošlo 456 + 164 Python testů,
devět Node sad, metadata/syntax, main protipříklady a čtyři původní auditní
kontrakty. Doplněný replay kontrakt následně prošel znovu.
Tyto syntetické kontroly nejsou důkaz celé fyzické noci či přihlášeného HA shellu.

## Chyby a slepé cesty vývoje nástroje

| Pokus | Výsledek a oprava |
|---|---|
| Hromadné čtení pomocných skriptů | Oříznutý výstup; přešlo se na jednotlivé úseky. |
| Zápis před vytvořením adresáře | ENOENT bez vytvoření souboru; adresář vytvořen před zápisem. |
| Záměna schémat vzorků | Podrobná inputs/session patří do priority_samples, nikoli ram_control_samples. |
| Fixture v1 | Chyběl model_available_at; doplněn syntetický čas, kontrola zůstala přísná. |
| Fixture v2 | Chyběl select priority; správná blokace vedla k opravě fixture, nikoli vypnutí kontroly. |
| Chybějící ideální model | Doplněn explicitní unavailable, bez fallbacku na jinou relaci. |
| Pomocná VM bez window | ReferenceError před změnou dashboardu; samostatná opravená verze doplnila stub. |
| Duplicitní expected v pomocném verifieru | SyntaxError před kontrolami; odstraněna nepoužitá převzatá deklarace. |
| Locale řazení času ve verifieru | Celé sekundy a mikrosekundy daly jiný pořádek; obě srovnávaná pole se řadí podle Date.parse. |
| Původní publikační balík | Automatická kontrola odmítla provozní MEMORY a hashe soukromých podkladů ve veřejném repozitáři. Zamítnutý balík se nepublikuje. |

Tento veřejný příspěvek je materiálně užší: pouze obecná metodika,
kód bez vstupních dat, syntetický test a syntetické fixture logy.
Neobsahuje provozní MEMORY, soukromé hashe, provozní čísla, DB, dashboard,
surové logy ani časové řady. Úplný soukromý audit zůstává odděleně na RPi.
