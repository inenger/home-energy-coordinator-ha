# DB-OPT-01 — bezztrátová optimalizace databáze priority_shadow 0.6.36

**Datum:** 17. 11. 2026. **Záměrně omezeno:** pouze `priority_shadow`, databáze `/data/evidence/evidence.sqlite` uvnitř addonu a jeho přenosná SQLite kopie v `/share/home-energy-priority-shadow`. Neprovádět žádné operace na Home Assistant `home-assistant_v2.db`, SolaX, Tesla, tarifu, původních HA automatizacích ani HEC LIVE. Režim `observe_only`.

## Zjištění (read-only)

- Přenosná kopie doplňku z 17.11.2026 08:10 SEČ: **429 359 104 B (429,36 MB)**, z toho **4 730 × 4 096 = 19 374 080 B** volných stránek (freelist). Pozor: je to 6hodinová přenosná kopie, nikoli živá interní DB v containeru; její velikost se může lišit.
- Velikost tabulek přenosné kopie: `journal_transport_outbox` ~115 MB, `priority_samples` ~86 MB, `soc_decisions` ~77 MB, `ram_control_samples` ~41 MB, `night_samples` ~38 MB. V 0.6.33 už byla provedena významná bezztrátová deduplikace SOC/priority včetně SHA.
- 14denní denní retence funguje a `journal_transport_archive` potvrzuje ACK. Nedokončená noc 30.10. (`status=incomplete`, jen 106,98 min pokrytí) je z bezpečnostních důvodů nedotknutelná; ostatní sealed dny mají prokazatelně platný SHA. Není bezpečné plošně smazat outbox/receipts nebo zkrátit 14denní detailní horizont bez dokladů pro replay a archiv.
- Samotné zrychlení SolaX Modbus z 5s na 1s **nemění periodu sampleru priority_shadow** (noc ~5s/day ~60s; oddělený rychlý model). Zlepšuje čerstvost fyzického měření a může růst hlavní DB Home Assistantu, která je **mimo toto zadání**.
- Recompression zlib level 6→9 na vzorku: outbox 0 %, ostatní vzorky 1,7–3,1 %. Není ospravedlnitelná změna kryptografických transportních BLOBů ani rozsáhlé přepisování trvalých SOC rozhodnutí kvůli jednotkám procent.

## Bezpečná optimalizace

`energy/offline_repack.py` je nový **explicitní operátorský jednorázový** režim po startu addonu 0.6.36, ale před spuštěním jakéhokoliv pracovníka. Nespouští se automaticky bez `/share/hec-db-repack-20261117/REQUEST.json` s přesným obsahem `{"action":"repack_lossless","mode":"observe_only","expected_release":"0.6.36"}`.

1. Z live DB udělá přes SQLite online backup **úplný neměnný originál** do /share, ověří quick_check a FK; nikdy nepřepíše originál při opakovaném pokusu.
2. `VACUUM INTO` udělá novou pracovní kopii. Žádný `DELETE`, `UPDATE` BLOBů, změna 14d/90d retence nebo rekomprese transportních dat.
3. Srovná kompletní definice schématu, všechny počty a high-water maxima, a **každý řádek včetně explicitního `rowid` a přesných bajtů všech BLOBů** ve všech tabulkách proti originálu. Při jakékoliv odchylce nezamění produkční databázi.
4. Před výměnou vyžaduje nezměněnou transakční hranici živé databáze. Novou kopii uloží vedle staré na stejné /data partition, `fsync`, checkpoint, atomic replace, post-swap quick_check/FK a count validation. Při chybě post-swap obnoví originál atomicky zpět.
5. Trvalá /share originální kopie a nativní Supervisor partial backup jsou oddělené body obnovy. Po úspěchu se označí `COMPLETED.json` a požadavek se archivuje; žádná další automatická přebalení za zády uživatele.

**Zkušební přebalení přenosné kopie:** 429 359 104 B → 409 526 272 B, **úspora 19 832 832 B (4,62 %)**. `quick_check=ok`, FK prázdné. Nezávisle potvrzena stejná SQLite metadata i data **47/47 tabulek, 289 566/289 566 řádků včetně rowid a přesného BLOB obsahu**. Reálný výsledek na aktuálním live souboru se může lišit. Test nepotvrzuje nový runtime sám o sobě.

**Ověření:** `priority_shadow/tests/test_offline_repack_0636.py` E2E synthetic rollback/source row identity, tampering reject, invalid request reject; `scripts/validate_versions.py`, `scripts/verify_documentation.py`, CI, a následný reálný readback. Žádný HA recorder purge, žádné úpravy `/homeassistant/home-assistant_v2.db`.

**Hranice očekávání:** jednorázové odstranění volných stránek SQLite nahradí zhruba 4–5 % z portabilní DB, nikoli 50 %. Nová data je budou znovu přidělovat; stávající ACK/sealed retenční mechanismus dál udržuje dlouhodobé množství detailů blízko 14dennímu oknu. Další ztrátová deduplikace dat vyžaduje explicitní návrh, samostatné testy a kalibrovaný důvod.
